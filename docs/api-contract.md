# Current API contract

The Go API accepts JSON and returns JSON errors as `{"error":"..."}`. Requests with invalid inputs return 400, missing sessions 401, failed origin/CSRF checks 403, and unavailable records 404. Authenticated mutations require the configured `Origin`, the session cookie, and the CSRF cookie value in `X-CSRF-Token`. Sessions are restored with `GET /api/auth/me`, which returns user `id`, `email`, and `name`. `PUT /api/profile` accepts a non-empty `name` of up to 80 characters. Registration accepts an email and non-empty `name` (up to 80 characters) and returns the same neutral response for new, pending and existing accounts. Pending accounts cannot sign in. Repeating registration or attempting to sign in to an unverified account requests a verification email, limited to one per account per minute and subject to IP rate limiting; sign-in failures have a generic response. The verification confirmation accepts a single-use token and a new 12–128 byte password. It atomically sets the password, marks the email verified, and revokes all sessions and outstanding verification and reset tokens. Older unverified accounts must also choose a new password when verifying; existing verified accounts remain unchanged. Password-reset links apply to verified accounts. `POST /api/auth/verification/check` and `POST /api/auth/password-reset/check` accept a token in the JSON body and return 204 when it is currently valid, or 400 with code `invalid_link` when it is invalid, expired, used, revoked, or ineligible. Checking does not consume a token; confirmation revalidates it atomically, so a link can still expire between the check and submission. Check endpoints require the configured origin and have a separate in-process IP limit. Local messages are captured by Mailpit.

`GET` and `PUT /api/settings` use `currency` (`IDR`, `USD`, `SGD`, or `AUD`), `locale` (`en` or `id-ID`), signed integer `openingBalance` in currency minor units, and `transactionEntryDefault` (`manual` or `scan`). IDR uses whole rupiah; USD, SGD, and AUD use 100 minor units per major unit. Changing the display currency relabels saved amounts without conversion. This preference chooses the initial view on the add-transaction page.

`/api/transactions` accepts `kind` (`income` or `expense`), positive integer `amount` in minor units, calendar `date` (`YYYY-MM-DD`), nullable `categoryId`, `description`, `merchant`, and `note`. Currency in responses is the user's current display currency. Category IDs must belong to the user and match the independent transaction kind. PUT replaces the editable fields. DELETE soft-deletes; POST `/:id/restore` restores within 30 days. `GET /deleted` lists eligible records. The API erases expired transactions on startup and hourly while running.

`POST /api/transactions/extract` accepts one multipart image field named `image`, requires an authenticated session, configured Origin, and CSRF token, and returns `{ "drafts": [...] }`. Each draft has description, kind, amount (integer minor units for the account currency), date, merchant, note, category, and uncertainFields. It does not create transaction records. JPEG, PNG, and WEBP images up to 8 MB are accepted; the API sends bytes directly to Gemini and does not persist them. Configure `GEMINI_API_KEY` in the API environment; `GEMINI_MODEL` optionally selects a model (default `gemini-3.5-flash-lite`). The endpoint is IP rate-limited, returns 503 when the key is unset or the scan provider is busy, and returns 502 for other provider failures.

`POST /api/transactions/batch` accepts `{ "transactions": [...] }` with 1–50 normal transaction inputs. It validates all records and category ownership, then creates them in one database transaction so a failed batch saves none.

List and `/export.csv` support `q`, `kind`, `category` (UUID or `uncategorized`), `from`, `to`, and `sort` (`date_desc`, `date_asc`, `amount_desc`, `amount_asc`; deleted lists also allow `deleted_desc`). Lists accept one-based `page` and `limit` (1–100), and return `transactions`, `total`, `page`, and `limit`. CSV exports all matching records in the selected order, independent of pagination. The account UI loads all pages and filters, sorts, paginates, and exports locally; server-side list and CSV endpoints are available but not yet wired to those controls.

`GET /api/categories` returns the user's active `categories`. POST and PUT `/api/categories[/:id]` accept `name` (1–80 characters), `kind`, nullable `parentId`, `icon`, and `color`. Names are case-insensitively unique per user and kind among active categories. Kind cannot change after creation; a parent must be an active top-level category of the same kind and owner. Deeper nesting and cycles are rejected. DELETE soft-deletes a category without an automatic purge or restore policy. Its active children become top-level; its transactions, including recently deleted ones, and active schedules become uncategorized. A category with active budgets cannot be deleted. Category and transaction assignment mutations are serialized per user.

`GET /api/budgets` returns active budgets with `id`, `categoryId`, positive integer `amount` in minor units, `period` (`weekly` or `monthly`), `spent`, `periodStart`, and `periodEnd`. An optional `on=YYYY-MM-DD` selects the calendar date used for current-period spending; without it, the API uses the current UTC date. The web client supplies its local date. Weeks start Monday and end Sunday; months use calendar boundaries. Spending includes active expense transactions assigned to the budget's category. A parent budget also includes direct child-category transactions. Parent and child budgets are reported separately, so their spending must not be added together as a single total. POST and PUT `/api/budgets[/:id]` accept `categoryId`, `amount`, and `period`; the category must be active, expense-kind, and owned by the user. One active budget per category and period is allowed. DELETE soft-deletes a budget without deleting transactions. Deleted-budget purge and restore behavior remains undecided.

## Recurring schedules

Authenticated `GET /api/recurring` returns active schedules and pending occurrence snapshots. `POST /api/recurring/sync` accepts `on` as a local calendar date and creates due occurrences through that date; it requires origin and CSRF checks. `POST /api/recurring` and `PUT /api/recurring/:id` accept description, categoryId, kind, amount, frequency, nextDate, paused and `on` (the local calendar date used to materialize due items before changes). `DELETE /api/recurring/:id` soft-deletes the schedule and its pending occurrences. `POST /api/recurring/occurrences/:id/skip` skips a pending occurrence; `POST /api/recurring/occurrences/:id/confirm` accepts transaction fields and atomically creates one transaction. Ownership and category kind are validated. Schedule edits leave already generated drafts unchanged. Resuming advances past dates missed while paused; pending drafts remain reviewable.
